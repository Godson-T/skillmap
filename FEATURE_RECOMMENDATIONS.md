# SkillMap — Feature Recommendations

## Where the product stands today

Every number and claim in today's report is generated by an LLM from a skill list. That
includes demand scores, declining-skill reasons, ROI, timelines and "50%+ of postings".
Nothing is measured.

For someone deciding what to spend the next six months learning, the report is
**directional inspiration, not evidence**. The `prod-hardening` branch now labels it
that way.

The biggest gap is not features. It is that **no output is grounded in real market
data**, and **nothing persists**, so users cannot act on the plan over time.

### What users actually need, and how well today's report covers it

| User | What they actually need | Covered today? |
|---|---|---|
| Job seeker | Which skills real postings for *my target role in my city* ask for, and which of those I lack | No. Model guess only |
| Career switcher | A realistic sequence and time budget that fits *my* available hours, plus proof the role pays | Partly. Generic timelines, no hours input, no real pay data |
| Upskiller | Track what I've learned, see readiness move, and get pointed at a credible course | No. No persistence; links are searches |

## Cost basis

- One analysis is about 550 input tokens and about 2,500 output tokens, including
  reasoning.
- On `openai/gpt-oss-120b` ($0.15 input / $0.60 output per 1M tokens) that is about
  **$0.0016 per report**.
- On the previous `qwen/qwen3.8-27b` Preview model ($0.80 / $4.00) it was about
  **$0.010 per report**, roughly 6× more.

Prices are from Groq's Supported Models page on 2026-11-19. They change, so re-check
them.

## Ranked list (impact ÷ effort)

### 1. Ground skill demand in real job postings

**Impact: very high. Effort: medium.**

- **Problem:**
  - "Rising skills" and "demand scores" are invented.
  - A switcher can't tell whether "Kubernetes" matters for *Data Engineer in India*.
- **Approach:**
  - Fetch about 50–200 live postings for the target role and location.
  - Extract skills with the existing taxonomy (`shared/skills.js`). The extraction is
    deterministic and needs no LLM.
  - Show "appears in X of N postings (source, fetched date)".
  - Let the LLM *explain* the measured frequencies instead of inventing them.
- **Data sources and caveats:**
  - **Greenhouse Job Board API**
    (`boards-api.greenhouse.io/v1/boards/{token}/jobs?content=true`) and the **Lever
    Postings API** (`api.lever.co/v0/postings/{site}`).
    - These are free, public and need no auth for GET.
    - The catch is that they are *per company*. You have to curate a list of board
      tokens, and the sample is biased toward startups and tech companies that use
      these ATSs.
    - The postings are the employers' content. Show aggregates and link out; don't
      republish job descriptions.
  - **Adzuna API**: covers the US, UK, India and many EU countries, and includes
    salary histograms.
    - The free key is "intended for evaluating the API".
    - The ToS permit publishing Adzuna listings or salary estimates and personal or
      undergraduate research. Other commercial use needs Adzuna's agreement.
    - Licensing therefore needs a decision from you. **⚠️ Your decision.**
  - **JSearch (RapidAPI)**: aggregates Google for Jobs.
    - It is a paid RapidAPI plan beyond a small free tier, with upstream ToS
      ambiguity. **⚠️ Paid provider — not chosen.**
- **Cost per request:**
  - Greenhouse/Lever: $0, plus about 1–3 s latency per board. Cache per role and
    location for 24 h.
  - Adzuna: free within quota, then commercial.
  - The LLM cost stays the same.
- **Risk:**
  - Low if shown as counts with "n=" and the source.
  - Small samples (n<30) must be flagged.
  - Taxonomy misses under-count niche skills. Show "other skills" rather than hide
    them.

### 2. Gap-to-plan tracking: save a profile and mark skills learned

**Impact: high. Effort: medium.**

- **Problem:** the report is single-use. Users can't track progress, so there's no
  reason to return.
- **Approach:**
  - **Phase A:** localStorage-only, with no account and no PII server-side. Mark a
    skill learned and readiness % updates, using the new normalized gap math.
  - **Phase B:** optional sign-in plus a database for cross-device use.
- **Data source:** first-party.
- **Cost:**
  - Phase A: $0.
  - Phase B: a hosted Postgres or Upstash free tier, which needs auth plus a
    deletion/export flow.
- **Risk:** low. Phase B adds privacy obligations, because skills and goals are
  career PII.

### 3. Weekly study plan fitted to available hours, plus an interview checklist

**Impact: high. Effort: low.**

- **Problem:**
  - Today's timelines ("6 months") ignore whether the user has 3 or 20 hours a week.
  - Switchers also need to know what interviews for the role test.
- **Approach:**
  - Add an "hours/week" input as a fixed enum: 3 / 5 / 10 / 20.
  - Generate a week-by-week plan from the missing skills, with deterministic
    scheduling in code and the LLM only for descriptions.
  - Add a role checklist of topics only, labelled as an AI estimate.
- **Data source:** LLM plus a deterministic scheduler.
- **Cost:** about +$0.001 per report.
- **Risk:** medium. Effort estimates per skill are guesses. Label them and let users
  adjust.

### 4. Resume upload that auto-extracts skills, confirmed by the user

**Impact: medium-high. Effort: medium.**

- **Problem:** typing skills is slow, and people under-list what they know.
- **Approach:**
  - Parse PDF/DOCX **in the browser** with pdf.js or mammoth, so the file never
    leaves the device.
  - Match against the taxonomy, then show chips the user confirms before analysis.
- **Data source:** the user's own file.
- **Cost:** $0 server-side. Only an LLM fallback for unmatched phrases would cost
  extra (≈$0.0005).
- **Risk:**
  - Low if client-side.
  - If you ever upload resumes server-side, you take on PII storage, retention and
    breach scope. Avoid that.

### 5. Location-specific salary bands from a cited source

**Impact: medium-high. Effort: medium.**

- **Problem:** the "ROI" text is invented, and money is the deciding factor for most
  switchers.
- **Data sources:**
  - **US:** the BLS OEWS program (annual, by SOC code and metro). It is available
    via the BLS Public Data API, where v2 needs a free registration key. It is
    public domain, so cite "BLS OEWS, May <year>".
  - **UK:** the ONS ASHE annual tables. They are published under the Open Government
    Licence and use broad SOC groups.
  - **EU:** Eurostat Structure of Earnings Survey. It is coarse and multi-year
    lagged.
  - **India:** there is no official occupation-level series fine enough for tech
    roles. Either use Adzuna salary histograms (licence decision above) or show "no
    cited data" rather than a guess.
- **Approach:**
  - Map each target role to SOC codes in a static table.
  - Show p25/median/p75 with the source and the reference period.
  - Cache data annually in a JSON committed to the repo.
- **Cost:** about $0 per request (static data). Refresh once a year.
- **Risk:**
  - The SOC↔role mapping is lossy. For example, "AI Engineer" maps to Software
    Developers 15-1252.
  - Say so in the UI.
  - Never blend in model numbers.

### 6. Feedback loop (👍/👎 per recommendation)

**Impact: medium. Effort: low.**

- **Problem:** there is no signal to evaluate prompt or model changes. Every model
  swap is a blind change, as the qwen and llama situation showed.
- **Approach:**
  - POST `{requestId, section, itemIndex, vote}` to `/api/feedback`. The request ID
    already exists after this branch.
  - Log it as a structured event, with no skills text.
  - Build a weekly eval sheet from it.
- **Cost:** $0 (logs) or the Upstash free tier.
- **Risk:** low. Rate-limit it like `/api/analyze`.

### 7. Course mapping with verified URLs

**Impact: medium. Effort: medium-high.**

- **Problem:** today's links are search pages. They are honest after this branch's
  relabelling, but low value.
- **Approach:**
  - Use a curated JSON of about 3 vetted courses per taxonomy skill. Prefer free and
    official docs, such as vendor learning paths.
  - Add a scheduled GitHub Action that HEAD-checks each URL weekly and opens an issue
    on 404s.
- **Data source:** manual curation.
  - Udemy and Coursera affiliate and catalog APIs have their own approval and ToS.
    **⚠️ Your decision if monetising.**
- **Cost:** $0 per request.
- **Risk:** link rot (mitigated by the checker). Curation bias should be disclosed.

### 8. Shareable, versioned reports with expiry

**Impact: medium. Effort: medium.**

- **Problem:** users want to show a mentor their plan.
- **Approach:**
  - Store the validated report JSON (not inputs) under an unguessable 128-bit ID.
  - Set a TTL (for example 30 days) and offer "revoke".
  - Version the report by schema version.
- **Data source:** first-party KV.
- **Cost:** Upstash free tier, or a few cents a month at small scale.
- **Risk:**
  - Shared reports reveal a person's skills and goals. Default to private.
  - Never index them (`noindex`).
  - **⚠️ Needs a public domain for links. Ask before changing it.**

## Recommended sequencing

1. **Now (this branch):** honesty labels, validation, cost controls. Done.
2. **Next 2 weeks:** #3 study plan + hours, #6 feedback, #2A local tracking. These
   cost no money and need no licensing.
3. **Then:** #1 with Greenhouse/Lever only (free), plus #5 for US/UK (public data).
4. **After your licensing decisions:** Adzuna (India/EU coverage and salaries), #7
   affiliate links, #8 sharing.

## Decisions you need to make

- Adzuna commercial licence vs. sticking to Greenhouse/Lever.
- Whether any paid provider (JSearch or similar) is acceptable.
- Whether to accept server-side storage of user data (Phase B tracking, sharing). That
  brings a privacy policy and deletion flow.
- Rate-limit store: Upstash Redis (free tier available) vs. none. The code supports
  both. Without it, limits are per serverless instance only.
