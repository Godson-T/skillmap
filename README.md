# SkillMap

Turn a list of skills into an encouraging, actionable career roadmap. You enter your
current skills, an optional target role and a location. SkillMap returns:

- a skill-topology graph
- rising and declining skills
- 2–3 career paths with timelines
- quick-win micro-skills
- learning searches

It also shows **what real job postings ask for**: skill counts measured from live
postings for your target role on public Greenhouse and Lever job boards, with the
sample size and source.

> **The AI roadmap is an estimate.** It is generated by a language model from your
> inputs, and the UI labels it that way. Only the "What Real Job Postings Ask For"
> section is measured data. See [FEATURE_RECOMMENDATIONS.md](FEATURE_RECOMMENDATIONS.md)
> for what's next.

## Quick start

```bash
npm ci
cp .env.example .env      # then set GROQ_API_KEY
npm run dev               # http://localhost:5173 (the API runs inside the Vite dev server)
```

Requires Node 22.12+ (Vite 8 / Vitest 5).

## Scripts

| Command | What it does |
|---|---|
| `npm run dev` | Vite dev server with `/api/analyze` mounted as middleware |
| `npm run build` / `npm run preview` | Production build; `preview` also mounts the API |
| `npm run lint` | ESLint (must pass in CI) |
| `npm test` | Unit and API-handler tests (Vitest, Groq mocked) |
| `npm run test:e2e` | Playwright smoke test of form → results (API mocked in-browser) |

The E2E test needs a Chromium. Either run `npx playwright install chromium`, or point
it at an existing Chrome:

```bash
PW_CHROMIUM_PATH=/path/to/chrome npm run test:e2e
```

## Environment variables

All variables are server-side only. None use the `VITE_` prefix, so none are bundled
into the browser. Full annotated list: [`.env.example`](.env.example).

| Variable | Default | Purpose |
|---|---|---|
| `GROQ_API_KEY` | **required** | Groq API key |
| `GROQ_MODEL` | `openai/gpt-oss-120b` | Model ID. Defaults to a Groq *Production* model |
| `LLM_TIMEOUT_MS` | `20000` | Per-attempt upstream timeout, clamped to 1–30 s. Both attempts share a 50 s deadline |
| `LLM_MAX_TOKENS` | `6000` | Completion budget, including reasoning tokens, clamped to 512–12000 |
| `ALLOWED_ORIGINS` | *(empty)* | Extra cross-origin callers (same-origin is always allowed) |
| `TRUST_PROXY` | *(empty)* | Read client IP and host from `X-Forwarded-*`. Automatic on Vercel; set only behind a proxy that overwrites those headers |
| `UPSTASH_REDIS_REST_URL` / `_TOKEN` | *(empty)* | Shared rate-limit store. `KV_REST_API_URL` / `_TOKEN` are also accepted |
| `RATE_LIMIT_PER_MINUTE` | `5` | Per client IP |
| `RATE_LIMIT_PER_DAY` | `40` | Per client IP |
| `DAILY_REQUEST_CAP` | `2000` | Global analyses per UTC day (budget guard) |
| `DEGRADED_DAILY_CAP` | `100` | Global cap while Redis is configured but unreachable (limits fall back to per-instance memory) |
| `RATE_LIMIT_SALT` | `skillmap` | Salt used to hash IPs into rate-limit keys. **Set it in production**; an error is logged if it is missing |

Malformed numeric values are reported in a `ratelimit_config` log line at startup and
the default is used.
| `MARKET_RATE_LIMIT_PER_MINUTE` | `10` | `/api/market`, per client IP (separate from the analysis budget) |
| `MARKET_RATE_LIMIT_PER_DAY` | `200` | `/api/market`, per client IP |

## Architecture

```
Browser (React, src/App.jsx)
   │  POST /api/analyze  { skills, goal, location }
   ▼
api/analyze.js (Vercel)  ──┐
vite.config.js (dev/preview) ──┴─► server/handler.js
        1. CORS (same-origin + ALLOWED_ORIGINS; never "*")
        2. body size cap (8 KB) + JSON parse
        3. input validation (server/schema.js, zod)
        4. rate limit: per-IP minute/day + global daily cap (server/rateLimit.js)
        5. LLM call (server/llm.js): JSON mode, 20 s timeout,
           one retry on invalid JSON / schema failure
        6. output validation + cleanup (server/schema.js ReportSchema)
        7. structured log line (server/log.js), sanitized error envelope (server/errors.js)
   ▼
{ requestId, report, meta: { model, promptVersion, estimate: true, disclaimer } }
```

| Path | Role |
|---|---|
| `server/prompt.js` | **The only copy** of the system prompt and user-message builder |
| `server/schema.js` | Input schema and report schema. Clamps numbers, defaults enums, drops dangling graph edges, strips invented citations |
| `shared/options.js` | Locations, roles, suggested skills and input limits, shared by the UI and the API |
| `shared/skills.js` | Skill taxonomy with aliases (`JS`→JavaScript, `k8s`→Kubernetes, …) and skill-gap math |
| `src/lib/graphLayout.js` | Deterministic, seeded force layout for the topology graph |
| `server/market/` | Live job-posting data: curated boards, title/location filters, skill extraction, cached aggregation |

### Live job-posting data (`POST /api/market`)

Input is `{ goal, location }`, validated like `/api/analyze`; a target role is
required. It needs no Groq key and runs in parallel with the AI report.

1. Fetch the job lists of the boards in `server/market/boards.js`. This is a fixed,
   server-side list, so user input never becomes part of a URL. Lists are cached for
   6 h.
2. Keep postings whose **title** matches the role (`server/market/filters.js`) and
   whose location matches the region. If fewer than 10 match locally, use all
   locations and say so.
3. Fetch full descriptions for matches only. That is at most 15 per company and 150
   in total, cached for 24 h.
4. Extract skills with the shared taxonomy (`server/market/extract.js`). This uses no
   LLM, so counts are reproducible. Common-word collisions ("go", "react to",
   "rest") are guarded against.
5. Return the top 15 skills as `count` and `share`, plus `sampleSize`, `scope`,
   `lowSample` (n < 30), companies, board health, the source, `fetchedAt` and up to
   6 example posting links. Results are cached for 1 h.

Caveats shown in the UI:

- The boards skew toward tech companies and startups.
- Dictionary matching under-counts niche tools.
- Small samples are flagged.

The UI shows aggregate counts and links out to postings; it does not republish job
descriptions.

### API contract

**Success (200):**

```json
{ "requestId": "…", "report": { "risingSkills": [], "knowledgeGraph": {}, "careerPaths": [],
  "dyingSkills": [], "topMicroSkills": [] }, "meta": { "model": "…", "estimate": true, "disclaimer": "…" } }
```

**Error:**

```json
{ "requestId": "…", "error": { "code": "INVALID_INPUT", "message": "…", "retryable": false,
  "issues": [{ "field": "skills", "message": "…" }] } }
```

| Status | Codes |
|---|---|
| 400 | `INVALID_JSON`, `INVALID_INPUT` |
| 403 | `ORIGIN_NOT_ALLOWED` |
| 405 | `METHOD_NOT_ALLOWED` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 429 | `RATE_LIMITED`, `DAILY_LIMIT` (with `Retry-After`) |
| 500 | `INTERNAL` (includes Groq 4xx request errors, which a retry cannot fix) |
| 502 | `BAD_OUTPUT`, `UPSTREAM_ERROR` |
| 503 | `UPSTREAM_BUSY` (Groq 429/5xx, with `retryAfterSeconds` when known), `SERVICE_UNAVAILABLE`, `GLOBAL_DAILY_CAP` |
| 504 | `TIMEOUT` |

`retryable` in the error body tells the client whether trying again could help.

Provider error bodies, the model's raw output and token usage are never returned to the
client.

### Limits

| Input | Limit |
|---|---|
| Skills | 1–25 items, ≤ 40 characters and ≤ 5 words each, ≤ 800 characters total. Letters (any script, including combining marks), numbers, spaces and `. + # / & ( ) ' - _` only. Text is NFC-normalized; newlines and tabs are rejected |
| `location` | One of `US`, `India`, `EU`, `UK`, `Remote` (case-insensitive) |
| `goal` | One of the 29 preset roles, or a custom role ≤ 60 characters and ≤ 8 words with the same character rules. Custom roles are kept on purpose, so users can type roles that are not in the list |

Model output is validated leniently: a malformed item (one bad edge, an empty skill)
is dropped rather than failing the whole report, over-long lists are truncated, and
non-numeric scores get neutral defaults. A section with no valid items still fails
validation and triggers the single retry.

User text is sent to the model as JSON inside a delimited `<profile>` block. The prompt
tells the model to treat that block as data, not instructions.

### Logging

Each request produces one JSON line, `event: "analyze"`. It contains:

- request ID, status and error code
- latency
- model, prompt version and attempts
- prompt, completion and total tokens
- skills **count**, location enum and goal kind (`none`, `preset` or `custom`)

It never contains the skills text, the goal text, the prompt, the IP or the key.
`/api/market` logs `event: "market"` with sample size, scope, boards OK, failed
detail fetches, `degraded` and `cached`.

Events worth alerting on:

| Event | Level | Meaning |
|---|---|---|
| `ratelimit_config` | error | Production without Redis, half-set Redis env, or missing salt (logged at startup) |
| `ratelimit_degraded` | error | Redis unreachable; limits fell back to memory with `DEGRADED_DAILY_CAP` (at most once a minute) |
| `market_boards_failed` | warn | One or more job boards failed, with the reason per board |
| `market_details_failed` | warn | Posting detail fetches failed; the result is marked `degraded` |

## Deploying (Vercel)

1. Import the repo and set `GROQ_API_KEY`.
2. Strongly recommended: add Upstash Redis from the Vercel Marketplace so the rate
   limits and daily cap are shared across instances. Without it they apply per warm
   instance only.
3. Set `RATE_LIMIT_SALT` to a random value.
4. `vercel.json` gives `/api/analyze` `maxDuration: 60` (the LLM client stops at 50 s)
   and `/api/market` 30 (worst case 23 s). Endpoints and limits are listed once in
   `server/routes.js`; `tests/routes.test.js` fails if they drift.

## Known limits

- CORS stops other *websites* from using your key. It does not stop scripts that call
  the API directly. The rate limits and daily cap are the real abuse and budget
  controls.
- The model has no live data. Demand scores, timelines and "upside" are estimates and
  are labelled as such. The job-posting section is measured, but from a curated set
  of company boards rather than the whole market.
- Board tokens can go stale as companies change ATS. Run `npm run boards:check` and
  edit `server/market/boards.js`.
- Learning links are search pages on Udemy, Coursera, freeCodeCamp and YouTube, not
  vetted courses.
